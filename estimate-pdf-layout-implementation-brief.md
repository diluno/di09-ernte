# Implementation brief: improve the estimate PDF layout

## Goal

Update the existing self-made estimate web app so its generated PDFs read as structured project proposals rather than one long invoice table.

The change must be reusable for future estimates. Do not hardcode the example project, bundle names, hours, prices, or page count.

## Reference output

The current reference is `Diluno-GmbH-Offerte-OF-2026-003 (1).pdf`:

- A4, three pages, generated by headless Chromium.
- Restrained black/grey Diluno visual style.
- Recipient and estimate metadata at the top.
- One flat list of line items with `Leistung`, `Std.`, `Ansatz`, and `CHF` columns.
- Bundle names are repeated in every line-item title.
- The final totals and assumptions appear only on page 3.

Keep the overall brand, typography, footer, document number, and page numbering. Improve hierarchy and readability rather than making the PDF decorative.

## Required changes

### 1. Introduce explicit sections/packages

Render line items in named sections such as:

- Konzeption & Projektleitung
- Bündel 1
- Bündel 2
- Bündel 3
- Bündel 4
- QA, Launch & Reserve

Each section should have:

- A visually distinct header, using a subtle light-grey background or a stronger horizontal rule.
- An optional descriptive title in addition to its label, for example `Bündel 1 — Regionale Webapp`.
- Its line items below it.
- A computed section subtotal showing hours and amount.

Do not repeat `Bündel 1 –`, `Bündel 2 –`, etc. in every task title once the item is displayed inside its section.

### 2. Separate task titles from descriptions

Each item should have separate `title` and `description` fields rather than one combined text string.

Render the task title in semibold/bold. Render the description beneath it in regular, slightly lighter text. Increase spacing between tasks, while keeping the line height within descriptions compact.

### 3. Simplify the numeric columns

When every item uses the same hourly rate:

- Remove the repeated `Ansatz` column from the detailed list.
- Show `Stundensatz: CHF 150.–` once near the summary or package overview.
- Use only `Leistung`, `Aufwand`, and `Betrag` in the details.

If an estimate contains different rates, retain the rate column automatically. Do not remove support for mixed-rate estimates.

Right-align hours and amounts and use tabular numerals. Give the CHF amount slightly more visual emphasis than the hours.

### 4. Add a summary near the project title

The most important figures must appear on page 1 directly below the project title:

| Aufwand | Exkl. MwSt | Inkl. MwSt |
| ---: | ---: | ---: |
| **422 h** | **CHF 63’300.–** | **CHF 68’427.30** |

These values must be computed from the estimate data. The figures above are only the validation values for the reference estimate.

Below this, add a compact package overview:

| Package | Hours | Amount |
| --- | ---: | ---: |
| Konzeption & Projektleitung | 54 h | CHF 8’100.– |
| Bündel 1 | 104 h | CHF 15’600.– |
| Bündel 2 | 66 h | CHF 9’900.– |
| Bündel 3 | 76 h | CHF 11’400.– |
| Bündel 4 | 72 h | CHF 10’800.– |
| QA, Launch & Reserve | 50 h | CHF 7’500.– |

The detailed scope should begin after this overview.

### 5. Improve metadata and header spacing

- Hide optional metadata rows such as `Datum` or `Gültig bis` when their values are empty. Do not render an em dash as a placeholder.
- Reduce the height of the logo/header area by roughly 10–15% so the project title and summary receive more emphasis.
- Preserve the current recipient block and estimate metadata structure.

### 6. Turn the final note into an assumptions section

Replace the dense closing paragraph with a `Grundlagen der Schätzung` section rendered as a short list.

For the reference estimate, the content is:

- Basis ist die bestehende Plattform mit Nuxt-Frontend, Craft CMS und Rechenmodell-API.
- Die inhaltliche Recherche zu Beratungsangeboten und kommunalen Reglementen erfolgt durch alliance F und die Partnerorganisationen.
- Anpassungen am Rechenmodell erfolgen in Abstimmung mit den wissenschaftlichen Partnern.

The underlying input should support a list of assumptions, not only one free-form paragraph. Preserve a fallback for existing estimates that still contain a single note string.

### 7. Improve print pagination

- Do not split an individual task row across pages.
- Do not leave a section header alone at the bottom of a page.
- Keep a section and its subtotal together when it fits; if a long section must continue, make the continuation visually clear.
- Repeat the detail column header on continuation pages where appropriate.
- Keep the final totals block together.
- Preserve `Offerte {number}` and `Seite x / y` in the footer on every page.
- Avoid clipped content, overlaps, and accidental blank pages in Chromium PDF output.

Use print CSS such as `break-inside`, `break-before`, and `break-after` where suitable, but adapt the implementation to the existing renderer.

## Suggested data structure

Prefer explicit structured data over parsing prefixes such as `Bündel 1 –` from display strings. Adapt this shape to the app’s existing conventions:

```json
{
  "hourlyRate": 150,
  "sections": [
    {
      "label": "Bündel 1",
      "title": "Regionale Webapp",
      "items": [
        {
          "title": "Technische Grundlage",
          "description": "Aufsetzen der eigenständigen regionalen Webapp …",
          "hours": 16,
          "hourlyRate": null
        }
      ]
    }
  ],
  "assumptions": [
    "Basis ist die bestehende Plattform …"
  ]
}
```

Rules:

- A line-item rate overrides the global hourly rate only when set.
- Derive item amounts, section totals, net total, tax, and gross total from the source data.
- Preserve backward compatibility with existing saved estimates. Add a migration or a safe legacy rendering path; do not rely on fragile string parsing at render time.
- Keep the current Swiss number formatting consistent throughout the PDF.

## Preferred page composition

1. Page 1: compact header, recipient and metadata, project title, cost summary, package overview, then the beginning of the detailed scope.
2. Following pages: clearly separated package sections with subtotals, followed by QA/launch/reserve.
3. End of document: net total, VAT, gross total, then `Grundlagen der Schätzung`.

The exact page count may vary with content. Do not force a three-page layout.

## Implementation constraints

- First inspect the current form, estimate data model, HTML/PDF template, and print stylesheet; follow the project’s existing architecture and naming conventions.
- Keep calculation/business logic unchanged except where structured grouping or optional global rates require a backwards-compatible extension.
- Do not add a new framework or a large UI dependency for this change.
- The web form should make section label/title, item title/description, and assumptions editable.
- Existing estimates must still open and generate valid PDFs.
- The on-screen preview and generated PDF should use the same hierarchy wherever practical.

## Acceptance criteria

- The reference estimate computes to 422 hours, CHF 63’300.00 excl. VAT, CHF 5’127.30 VAT, and CHF 68’427.30 incl. VAT.
- Its six package totals match the package overview above.
- Page 1 shows the key totals before the detailed scope.
- Bundles are recognizable as sections without reading repeated prefixes.
- Blank metadata rows are absent.
- The hourly rate appears once when all items share it; mixed-rate estimates still show per-item rates.
- Task titles and descriptions have visibly different typographic treatment.
- No item row or totals block is split across pages.
- The PDF has no clipping, overlap, orphaned section headers, or blank trailing page.
- The footer and page numbering remain correct on every page.
- Verify at least one short estimate, the supplied reference estimate, and a long estimate that spans additional pages.
